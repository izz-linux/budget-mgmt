Budget Manager — Code Review

17 August 2026 · branch claude/budget-mgmt-next · 18 fixes across backend/ and frontend/

Read this first: four tests were already failing before any change

The test suite was red on main when this review started. Four tests failed before a single line was edited:

  • TestAutoAssign_MatchesBillsToPeriods
  • TestAutoAssign_UsesFirstPeriodWhenNoneBeforeDueDate
  • TestAutoAssign_BiweeklyFallsBackWithoutAnchor
  • TestAutoAssign_QuarterlyFallsBackWithoutAnchor

They hard-coded pay dates in early 2026 which have since passed. AutoAssign deliberately ignores pay periods before today, so no INSERT happened and the mock expectations went unmet. This was a pre-existing failure of the tests, not something these changes introduced and not a product regression. The tests were also weaker than they appeared — see Tests.

Critical Hangs, data loss, and silently broken features

Each of these could destroy user data, permanently wedge a request, or leave a shipped feature doing nothing at all.

01 Unbounded loop on an out-of-range weekday

backend/internal/services/period_generator.go — generateWeekly, generateSemiMonthly

What was wrong
The search for the first matching weekday advanced one day at a time until current.Weekday() equalled the configured value: 
for current.Weekday() != targetWeekday {
    current = current.AddDate(0, 0, 1)
}
Why it mattered
time.Weekday() only ever returns 0–6. A stored weekday outside that range — 7, -1, 99 — never matched, so the loop ran forever. The request goroutine was pinned for the life of the process, leaking one goroutine per attempt. The related generateSemiMonthly accepted day 0, which time.Date normalises backwards into the previous month, silently producing pay dates outside the requested window.
Fix
Validate the weekday is 0–6 and each semimonthly day is 1–31, returning an error instead of looping. A watchdog test now proves the generator returns rather than hangs.

02 schedule_detail was never validated

backend/internal/handlers/income.go — Create, Update

What was wrong
Create validated only the pay_schedule string and passed schedule_detail straight to the database untouched. Update validated neither, and so happily accepted a pay_schedule of "daily" that Create rejects.
Why it mattered
This is the front door for bug #1: it is how a weekday of 99 reached the database in the first place. The generator was the symptom; this was the cause.
Fix
One shared validateSchedule checks the detail against the schedule — weekly needs a weekday 0–6, biweekly a YYYY-MM-DD anchor, semimonthly exactly two days each 1–31, one-time a YYYY-MM-DD date. Create calls it directly. Update is the subtle case: either half of the pair can change independently, so when either is touched it SELECTs the current row and validates the resulting combination.

03 Optimizer applied a batch of moves with no transaction

backend/internal/handlers/optimizer.go — Apply

What was wrong
Each move was a DELETE followed by an INSERT, issued as separate statements straight on the pool. Three separate defects compounded:
  • No transaction — a failure partway through a batch left earlier assignments deleted with nothing put back.
  • The target period was never checked, so a bad to_period_id destroyed rows before failing.
  • The optimizer produces a chain of moves, so one assignment can be moved twice (A→B then B→C). The first move replaces the row and gives it a new id; the second still referenced the old id and 404'd — after the first had already committed its delete.
Why it mattered
Straightforward destructive data loss. The user clicks "Apply", something fails halfway, and bills simply vanish from the budget.
Fix
The whole batch runs in one transaction (matching the existing bills.Reorder pattern). Every target period is verified to exist before the first delete. A map of original assignment id → current live id lets chained moves resolve to the row that actually exists.

04 Sinking fund silently ate a bill's real assignment

backend/internal/handlers/sinking_fund.go — Apply

What was wrong
The installment upsert used an unguarded ON CONFLICT (bill_id, pay_period_id) DO UPDATE. If the bill already had an ordinary assignment in one of the chosen periods, that row was rewritten into a sinking-fund installment.
Why it mattered
The damage only surfaced later. Clear() deletes WHERE is_sinking_fund = true AND sinking_fund_for_period_id = $2 — so clearing the sinking fund deleted the user's ordinary assignment outright. A real, planned bill payment disappeared with no trace and no error.
Fix
The DO UPDATE now carries a WHERE that only matches rows already flagged as installments for this same target period. When it matches nothing, Postgres returns no row; the handler treats that pgx.ErrNoRows as "this period is occupied, skip it" and carries on with the remaining periods.

05 force on auto-assign was unreachable dead code

backend/internal/handlers/assignments.go — AutoAssign / assignMonthly

What was wrong
The two guards ran in this order: 
if existingBillMonths[bm] { continue }
if !req.Force && manuallyMovedBills[bm] { continue }
Every manually-moved bill is also an existing bill for that month, so manuallyMovedBills is a strict subset of existingBillMonths. The first branch always fired first and the second was never reached.
Why it mattered
The force flag did nothing whatsoever. Users asking to re-run assignment and override their manual moves got silence and no error.
Fix
Reordering alone would have been worse than the bug: the function only ever INSERTs, so force would have left the bill assigned to two periods in the same month. The corrected behaviour is to delete the manual placement(s) for that bill+month first, then insert on the computed period — and to do nothing at all when the manual placement already equals the computed one, avoiding pointless churn. The period ids holding manual placements are captured during the existing pre-fetch, so this costs no extra query.
Also fixed here
assignMonthly is a closure; a bare return after models.WriteError did not stop the handler, which then wrote a second response body onto the same ResponseWriter. It now returns an error handled at the call site. Relatedly, insertAssignment swallowed every scan error and returned nil, so a genuine failure was indistinguishable from a benign ON CONFLICT DO NOTHING; it now distinguishes the two and propagates real errors.

Correctness Wrong numbers, wrong dates, wrong on some runs

These produce plausible-looking but incorrect output — the most expensive kind of bug in a budgeting tool, because the user has no reason to distrust it.

06 Period totals counted soft-deleted bills

backend/internal/handlers/{budget_grid,periods,dashboard}.go

What was wrong
COALESCE(SUM(ba.planned_amount), 0) summed every assignment in the period, including ones belonging to bills with is_active = false.
Why it mattered
The grid only renders active bills. So the Total and Remaining rows disagreed with the visible rows above them, and no amount of staring at the grid explained the difference. Deleting a bill made the arithmetic wrong forever after.
Fix
Join through bills and count only active ones: LEFT JOIN bills ab ON ab.id = ba.bill_id AND ab.is_active = true, then SUM(...) FILTER (WHERE ab.id IS NOT NULL). The grid's assignment fetch is filtered on b.is_active too, and dashboard.go gained the inc.is_active = true predicate that the grid and periods queries already had.

07 Upcoming bills panel emptied at month end

backend/internal/handlers/dashboard.go — Summary

What was wrong
The 7-day window was computed as arithmetic on the day number: 
dayOfMonth := now.Day()
weekLater  := dayOfMonth + 7
// ... WHERE due_day BETWEEN $1 AND $2
Why it mattered
On the 28th this searched for days 28 through 35. Days 32–35 do not exist, and bills due on the 1st–4th of next month — which genuinely are within seven days — were never matched. The panel went blank at the end of every month, exactly when rent and mortgage are due.
Fix
Build the actual list of calendar days the window covers (crossing the month boundary properly, de-duplicated) and query due_day = ANY($1).

08 Sinking fund under-funded and lost cents

backend/internal/services/sinking_fund.go — PlanSinkingFund

What was wrong
The planner split the bill evenly, capped each period at its available surplus — and then stopped. Whatever a tight period could not absorb was simply reported as a shortfall. It also truncated each installment with float64(int(x*100))/100, losing up to a cent per period.
Why it mattered
$600 across three periods where the first has zero headroom funded only $400 and reported a $200 shortfall — while the two later periods sat there with ample unused surplus. The tool told the user they could not afford something they could comfortably afford.
Fix
Rewritten in integer cents, in two passes. Pass one spreads evenly capped by each period's headroom, giving remainder cents to the earliest periods. Pass two redistributes any remaining shortfall onto periods that still have room. A period's available surplus (income − assigned − buffer) is never exceeded, and a genuine shortfall — where the money really is not there — is still reported honestly.

09 "Today" was midnight UTC, not midnight local

backend/internal/handlers/assignments.go

What was wrong
time.Now().Truncate(24 * time.Hour). Truncate measures from the zero instant, not from the local day boundary, so it yields midnight UTC.
Why it mattered
For most of the world that is the wrong day. Since AutoAssign skips periods before "today", a period could be wrongly included or excluded near the date boundary.
Fix
Build it explicitly from the local year/month/day, expressed in UTC to match how pgx decodes a DATE column.

10 Regenerating periods wiped hand-edited income

backend/internal/handlers/periods.go — Generate

What was wrong
expected_amount = COALESCE(EXCLUDED.expected_amount, pay_periods.expected_amount). EXCLUDED is the income source's default and is rarely null, so it essentially always won.
Why it mattered
Any per-period income the user had adjusted by hand — an overtime cheque, a smaller pay week — was silently reset to the source default every time periods were regenerated. Regeneration happens automatically when the grid loads a new range.
Fix
Swap the arguments so the stored value wins and the default only fills a genuine null.

11 Import categorisation differed between runs

backend/internal/services/xlsx_importer.go — guessCategory

What was wrong
Category keywords lived in a map[string][]string and the function ranged over it. Go randomises map iteration order deliberately.
Why it mattered
"Car Insurance" matches both insurance and transportation. Whichever the range happened to reach first won, so importing the same spreadsheet twice filed the same bill under different categories — non-reproducible behaviour with no error to explain it.
Fix
An ordered slice with specific rules ahead of general ones, so "car payment" and "car insurance" are tested before the bare "insurance". Verified stable over 500 repeats.

12 Surplus months came back in random order

backend/internal/services/surplus_detector.go — Detect

What was wrong
The result was built by ranging over a map keyed by month — the same map-ordering trap as #11.
Why it mattered
The surplus list reshuffled on every request. The UI renders it in the order received, so the same data looked different each time the user opened the page.
Fix
Collect the month keys and sort them. The "2006-01" format sorts lexicographically and chronologically, so a plain string sort is correct.

13 A password with punctuation corrupted the database URL

backend/internal/config/config.go — DatabaseURL

What was wrong
The DSN was assembled with fmt.Sprintf, interpolating the password raw.
Why it mattered
A password containing @, /, ? or : changed the structure of the URL — everything after an @ parses as the host, a ? starts the query string. The failure mode is a confusing connection error at startup that points nowhere near the password.
Fix
Build it with net/url: url.UserPassword percent-encodes the credentials and net.JoinHostPort brackets IPv6 hosts correctly.

14 Turnstile verification had no timeout

backend/internal/auth/auth.go — VerifyTurnstile

What was wrong
http.PostForm uses http.DefaultClient, which has no timeout at all.
Why it mattered
An unresponsive Cloudflare would hang the login handler indefinitely. Every login attempt during an outage would pile up another stuck goroutine holding a connection.
Fix
A package-level http.Client with a 10-second timeout.

15 Login response time revealed valid usernames

backend/internal/handlers/auth.go — Login

What was wrong
A wrong username returned early, skipping the bcrypt comparison entirely.
Why it mattered
bcrypt is deliberately slow — that is the whole point of it. Skipping it made a wrong-username response measurably faster than a wrong-password one, so an attacker could enumerate valid usernames by timing alone, with no error message needed.
Fix
Both checks always run, and the username is compared with crypto/subtle.ConstantTimeCompare. The two results are combined only after both have completed.

16 Month navigation skipped February and went backwards

frontend/src/utils/date.ts · components/budget-grid/BudgetGrid.tsx — shiftRange

What was wrong
Three compounding mistakes in five lines: new Date(str) parses YYYY-MM-DD as UTC, Date.setMonth() overflows rather than clamping, and toISOString() converts back to UTC.
Why it mattered
Shifting 2026-01-31 forward one month gave 2026-03-03 — February skipped entirely. Worse, shifting 2026-03-31 back one month gave that same 2026-03-03, moving the date forward. The back button moved you forwards.
Fix
New toISODateString(d) formats from local calendar fields rather than toISOString(). New addMonths(dateStr, months) shifts on the 1st of the month — where no overflow is possible — then clamps the day to the target month's length. Both build on the existing parseLocalDate helper. Verified: Jan 31 +1 → Feb 28, Mar 31 −1 → Feb 28, and Jan 31 +1 in the 2024 leap year → Feb 29.

17 Entering 0 did nothing; entering text cleared the amount

frontend/src/components/budget-grid/BudgetGrid.tsx — handleCellSave, handlePeriodAmountSave

What was wrong
Creation was guarded by else if (amount) — a falsy check. And the value came straight from Number(text) with no validation.
Why it mattered
Two distinct failures. A $0 assignment is perfectly legitimate (a bill you are skipping this cycle) but 0 is falsy, so nothing was created and the user got no feedback. Separately, non-numeric text became NaN, which JSON.stringify turns into null — silently wiping an existing amount because of a typo.
Fix
One parseAmount helper returning number (a real value, 0 included), null (deliberately cleared), or undefined (unparseable → skip the write entirely). Used by both save handlers.

18 API client dropped headers; optimizer bypassed the client

frontend/src/api/client.ts · components/optimizer/OptimizerView.tsx

What was wrong
request() spread ...options after the merged headers object, so any caller passing its own headers replaced the merge wholesale and lost Content-Type. Separately, OptimizerView called raw fetch() for all three of its endpoints.
Why it mattered
The header bug is a landmine for the next caller rather than an active break. The raw fetch() calls were live, though: they skipped credentials: 'include', the 401→login redirect, and the server's error-message unwrapping — so an expired session on the optimizer page produced a generic failure instead of a redirect to login.
Fix
Spread options first so the merged headers survive. OptimizerView now uses the shared api.post/api.get, which also unwrap json.data, removing that duplication.

Tests Repairing the suite, then covering the fixes

The four pre-existing failures were not merely stale — they were structurally unable to catch the thing they claimed to test.

Why the four failing tests were weaker than they looked

Stale dates
They hard-coded pay dates in early 2026. Those dates have passed, and AutoAssign ignores periods before today, so no INSERT was ever attempted.
Wrong column count
Their mock rows returned 14 columns while the handler scans 16 — is_sinking_fund and sinking_fund_for_period_id were missing.
Swallowed errors
insertAssignment discarded scan errors and returned nil. Combined with the column mismatch, these tests would have passed while the handler silently created nothing at all.
Assertion gap
They asserted only on mock expectations, never on the returned assignment — so "the right row landed in the right period" was never actually checked.
Fix
A futureMonth(n) helper builds dates relative to time.Now(), used for both the pay dates and the from/to range, so the tests cannot go stale again. Fixtures return the 16 columns actually scanned. Tests now assert on the decoded response body. Three neighbouring anchor-based tests had the same 14-column fixtures and were repaired alongside them.

Deferred Found, but deliberately not changed

Each of these is a real problem. None was fixed here, because fixing it alters product behaviour in a way that is a judgement call rather than a defect correction. These need a human decision.

(a) The optimizer's projection assumes you apply the whole chain

The optimizer computes a chain of moves and reports a single projected minimum balance that only holds if every move in that chain is applied. The UI lets the user tick an arbitrary subset and apply just those.

So the outcome can differ from the headline number the user was shown, with nothing indicating the discrepancy. Resolving it means choosing a product behaviour: recompute the projection as the selection changes, disable partial selection, or show a caveat. That is a design decision.

(b) canPayFrom compares bare day-of-month

The optimizer's feasibility check is payDay <= dueDay — a comparison of day numbers with no month context. A bill can therefore never be moved to a later paycheck within the same month.

The practical effect is that the optimizer explores a far smaller search space than it appears to, and will report "already optimal" for arrangements it simply never considered. Fixing it means comparing real dates, which would change the suggestions the tool produces for existing users.

(c) Sinking funds can reserve from paychecks already spent

Candidate periods are selected with only pp.pay_date < target and no lower bound. There is nothing stopping the planner reaching back into paychecks that have already been received and spent, and reserving money from them.

The inactive-income-source half of this problem was fixed (period totals now exclude inactive sources — see #6). The missing lower bound was left alone: choosing where the floor belongs — today, the current period, an explicit user-supplied start — is a product decision, not a bug fix.

(d) Tombstones are permanent, and auth is all-or-nothing

Tombstones never expire. deleted_bill_periods rows are written on delete and never cleared. Deleting a bill from a period once means auto-assign can never place it there again — permanently, with no UI to undo it. Adding expiry or a reset needs a decision about what users expect "delete" to mean.

AuthEnabled() requires all three of AUTH_USERNAME, AUTH_PASSWORD_HASH and JWT_SECRET. If any one is missing or misspelled, authentication is silently disabled and the entire API is served unauthenticated. One typo in a deployment config is enough. main.go does log a warning, which is the only signal. Failing closed would be safer but would break any deployment intentionally running without auth — so this is deliberately left for the owner to decide.

No frontend test runner is configured. The frontend has no test framework at all, so fixes #16–#18 are covered only by tsc and the production build. The date-shifting logic in particular is exactly the kind of pure function that unit tests cover well, and would be the natural first thing to test if a runner is added.
